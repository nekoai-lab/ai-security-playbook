AIに「利用者が画像を送れるようにして」と頼みました。自分の画像を選ぶとプレビューが出て、保存した後も表示できます。

その確認で、何が分かったでしょうか。画面に表示できたことと、保存されたファイルを誰が開けるか、解析に使うプログラムが何をするかは、別の確認です。

この記事は、**個人開発で画像や資料のアップロード機能を付ける人**に向けています。正常な画像の動作確認から、受け取る・調べる・置く・見せるという処理の境界へ進みます。

<LessonScene id="uploads-and-input" />

## 選ぶ、受け取る、解析する、公開するを分ける

**アップロード**は、端末からファイルを送ることです。**解析**は、画像の大きさや文書の内容などをプログラムが読み取ること。受け取ったファイルを、まだ解析していない段階もあります。

<UploadVisual kind="flow" />

例えば、プロフィール画像を受け取り、縮小画像を作り、保存して利用者へ返す機能を考えます。元画像と縮小画像が別の保存先へ置かれる場合もあります。「サムネイルだけ見せる」つもりでも、元画像のURLから取得できないかは別に確かめます。

受付時の成功、解析の成功、公開の完了は、それぞれ違う状態です。処理を後から行う構成なら、検査中のファイルを誰へ見せるかも決めます。

<span id="checks"></span>

## 画面で選べる種類は、サーバーの検査ではない

次のHTMLは、ファイル選択画面でPNG画像を選びやすくする例です。アプリへ組み込む前の、表示側の小さな部品として見てください。

```html
<input type="file" accept="image/png">
```

`accept`は選択のヒントで、ファイルの中身を検証する仕組みではありません。MDNも、サーバー側での確認が必要だと説明しています。[MDN：accept属性](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/accept)

**Content-Type**は、通信で申告されるデータの種類です。`image/png`ならPNGとして送るという申告ですが、申告と実際の内容が同じとは限りません。拡張子も、ファイル名の一部です。

<UploadVisual kind="checks" />

受け取る側では、業務で必要な形式を決め、申告された種類と実際の内容を照合します。画像を受ける必要しかないのに、文書や圧縮ファイルまで一緒に受ける機能へ広げない、という選び方もできます。[OWASP：アップロードの検査](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)

<CatGuide pose="think" title="名前・申告・中身は、別の情報">
画像らしい名前と、画像としての内容を分けます。さらに、形式が読めることと、見せてよい相手が決まることも別です。
</CatGuide>

## 先頭が画像形式でも、画像の検証は終わっていない

ファイルの先頭には、形式を示す目印があるものがあります。ここではPNGの先頭8バイト、つまり8個の小さな数値を、架空のデータで比べます。暗号による本人確認の署名とは別の、形式の目印です。

**自分のPCのNode.js**で動く観察用の例です。ファイルの読み書き、アップロード、画像の展開は行いません。数値の配列は完全な画像ではなく、検査の限界を見るためのものです。

```js
const pngPrefix = [137, 80, 78, 71, 13, 10, 26, 10];
function headerStage(bytes, maxBytes = 1_000_000) {
  if (!Number.isInteger(maxBytes) || maxBytes < 8) {
    throw new Error("上限の設定を確認");
  }
  if (!Array.isArray(bytes) || bytes.some((n) => !Number.isInteger(n) || n < 0 || n > 255)) {
    return "バイト列を確認できない";
  }
  if (bytes.length > maxBytes) return "サイズ上限を超える";
  if (!pngPrefix.every((n, i) => bytes[i] === n)) return "先頭形式が違う";
  return "先頭8バイトのみ一致。解析は未確認";
}
console.log(headerStage([137, 80, 78, 71, 13, 10, 26, 10]));
console.log(headerStage([68, 69, 77, 79]));
```

```text
先頭8バイトのみ一致。解析は未確認
先頭形式が違う
```

先頭の目印しかない、不完全なデータでも最初の結果になります。**「PNG画像として正しい」「有害な内容がない」「公開してよい」と判定した結果ではありません。** これは観察用の例です。本番の検証器には使いません。

例の100万バイトは観察用の設定で、すべてのサービスへの推奨値ではありません。また、この例は配列を既に受け取っています。実サービスでは、巨大な内容を全部メモリへ読み込む前に、受付や読込段階の上限も必要です。

## 画像を読む処理にも、時間と権限がある

画像の縮小や文書の文字抽出には、形式を読む**パーサー**や変換用のライブラリを使います。そのプログラムにも、読み書きできるファイル、通信先、実行時間やメモリの範囲があります。

<UploadVisual kind="processing" />

ファイルが小さくても、展開後の大きさや処理時間が小さいとは限りません。業務に合う形式・大きさ・処理量を決め、解析処理が失敗したときに、成功へ読み替えない状態管理を考えます。検査に使う部品の更新も、アプリ本体の更新とは別に追います。

ウイルス検査を入れる場合も、それだけで全形式・全攻撃を検出できるとは限りません。外部サービスへ検査を頼むなら、元ファイルがその相手へ渡ることを含め、情報の取扱条件を確認します。[企業向けAIと実データの扱い](/ai-security-playbook/learn/approved-ai-data/)と同じように、接続先まで見ます。

<UploadComparison />

例えば検査サービスのタイムアウトは、「何も検出されなかった」と同じではありません。検査中、形式不正、処理失敗、確認完了を分けます。公開前の確認が必要なファイルは、失敗時もその確認を飛ばして公開しないようにします。

## 保存できた後、誰が取り出せるかを確かめる

**オブジェクトストレージ**は、画像などのファイルを保存するサービスです。ログインした人がアップロードしたことだけでは、保存先でその人だけが読めると決まりません。

<UploadVisual kind="storage" />

ファイルを識別するIDと、アップロードした利用者の対応を持ち、取得・上書き・削除などで権限を確認します。元のファイル名をそのまま保存先の場所として使うのではなく、アプリ側で管理するIDを使う設計を考えます。他の利用者の既存ファイルへ上書きできないかも確認します。

**署名付きURL**は、期限などの条件を付けてファイルへアクセスする仕組みです。例えばAmazon S3は、そのURLを持つ人が使える認証情報として扱うよう説明しています。URLを知っている人へ権限が渡るため、短い期限でも無制限に公開してよい文字列ではありません。[AWS：署名付きURL](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)

S3の署名付きURLは期限内に複数回使え、アップロード先に同じキーがあれば既存オブジェクトを置き換える場合があります。「1回限り」「新規作成だけ」という想定なら、そのまま同じ意味にはなりません。利用する方式と、保存先のキーや権限を確認します。

<CatGuide pose="point" title="URLが開けた。それは誰の権限？">
自分のテスト用AとB、未ログインを分けて、返るべきファイルと返してはいけないファイルを確かめます。実際の利用者の資料で試す必要はありません。
</CatGuide>

<UploadVisual kind="permissions" />

検証用の無害なファイルで、AのファイルをBが取得・削除できないか、URLを外へコピーしたときにどうなるかを確認します。元画像、縮小画像、解析結果、一覧に出る名前も対象です。別の保存先や配信経路があるなら、それぞれ確認します。

## 画像の解析処理から、公表された脆弱性

**分類：脆弱性の公表。** GitLabは2021年11月4日の当事者記事で、画像ファイルを解析するExifToolに関係するCVE-2021-22205について、外部から見える自己管理インスタンスでの悪用報告を確認したと説明しています。修正は同年4月14日に公開され、GitLab.comの利用者は影響しないと区別されています。

[GitLabの当事者公表](https://about.gitlab.com/blog/action-needed-in-response-to-cve2021-22205/)

この問題は、画像の解析からサーバー上の意図しないコマンド実行につながるものでした。自分のアプリでも同じ問題が起きると断定する事例ではありません。「画像を読むだけ」の部品も、アプリが実行するプログラムであり、更新と権限の対象になるという学びです。今のGitLabにも未修正で残っているという説明や、攻撃手順の再現にはしません。

## 誰が、どの段階を確認するか

### 機能を作る人：受付と取得の条件を設計する

画面の選択制限と、サーバーや保存サービスの検査を分けます。認める形式、サイズ、件数、利用者と保存先の対応、取得・変更・削除の権限を確認します。画面を通る正常なファイルだけで検証を終えません。

### 運用する人：解析処理と失敗時を確認する

解析する部品の版、処理の権限、時間・容量の制限、検査中やエラー時の状態を確認します。保存したまま失敗したファイルの保持や再処理、利用量の異常をどう扱うかも決めます。根拠なく一括削除する運用にはしません。

### 情報を扱う人：見せる範囲を決める

画像や文書に含まれる情報と、利用目的、閲覧者、外部の解析先を確認します。利用者へ公開範囲を説明するなら、実際のURLや取得権限でも同じ動作になっているかを照合します。

## 受け取る機能を公開する前のチェック

- **受付：** 必要な形式とサイズ・件数を決め、画面だけでなく受信側でも確認する仕組みがある。
- **内容：** 名前・Content-Type・先頭形式・実際の解析を別の確認として扱う。先頭だけの一致を検証完了としない。
- **解析：** 利用する部品の版と、使える権限・処理量・失敗時の状態を確認した。
- **保存：** アプリが管理するIDと利用者の対応があり、他のファイルへの上書きや公開設定を確認した。
- **取得：** 自分のA/B/未ログインのテストで、元画像と派生物の許可・拒否を確かめた。
- **URL：** 署名付きURLの対象、期限、再利用や上書きの条件を確認し、不要に共有・記録していない。
- **異常時：** 検査失敗を確認済みにせず、問い合わせ先・再処理・保持の扱いが分かる。
