APIキーを新しく発行し、クラウドの設定も書き換えました。新しく起動したアプリから、外部APIへ接続できることも確認しています。

ところが翌朝、定期処理だけが失敗しました。画面からの操作は動くのに、夜間の処理は古いキーを使っていたのです。

これは仕組みを説明する架空の場面です。この記事は、**AIで作ったアプリを公開し、外部APIのキーを自分で管理する人**に向けたもの。「新しい値を保存できた」の先で、どこまで交換が届いたかを見ていきます。

<LessonScene id="secret-rotation" />

## キーを替える場所は、一つではない

**シークレット**は、APIキーやパスワードなど、秘密として扱う情報です。**ローテーション**は、それを新しいものへ交換すること。ここでは外部APIへの接続に使うキーを扱います。

「設定を更新した」という言葉には、少なくとも3つの違う状態が隠れています。

<RotationVisual kind="layers" />

シークレット管理サービスへ新しいキーを保存しても、外部APIの発行元が古いキーを無効にしたとは限りません。また、保存済みの値と、アプリのメモリに読み込まれた値は別です。

**プロセス**は、起動して動いているプログラムです。起動時にキーを一度だけ読み、接続用の**クライアント**を作る実装なら、保存先を更新しても、そのクライアントは古い値を持ち続けることがあります。

例えば「朝から動いているWebアプリ」「夜だけ動く集計」「手元の管理用スクリプト」は、同じキーを使っていても別の利用者です。Webアプリ一つの成功を、全部の成功へ広げないのが出発点です。

<CatGuide pose="think" title="更新したのは、どの場所？">
「新しいキーにした」を、「発行した」「保存した」「この実行が読み込んだ」「古いキーを失効した」に言い換えると、残った仕事を見つけやすくなります。
</CatGuide>

## Cloud Runでは、読むタイミングを区別する

一例としてCloud Runでは、シークレットを**環境変数**、つまり実行環境からプログラムへ渡す値として使う場合、インスタンスの起動時に値が解決されます。`latest`を指定しても、起動済みの値が常に追従するという意味ではありません。Googleは環境変数では特定の版を指定することを推奨しています。[Cloud Run公式資料](https://docs.cloud.google.com/run/docs/configuring/services/secrets)

一方、ファイルとして接続する**ボリュームマウント**では読取時に値を取得します。新しい版を追う設定でも、アプリが起動時に読んでメモリへ保存したままなら、アプリ側の使う値まで自動で替わるとは限りません。特定の版に固定したファイルは、その指定も別に確認します。

<RotationVisual kind="read" />

この違いはCloud Runの例です。別のクラウド、ライブラリ、CIでは、再読込・キャッシュ・再起動の仕様をそれぞれ確認します。毎回取得する設計にも、通信の失敗や遅延、利用料金という別の考慮があります。「毎回取得すれば解決」ではなく、取得失敗時に古い値を使うのか、処理を止めるのかも決めます。

Cloud Runの公式資料では、環境変数の取得に失敗すると起動できず、マウントされた値も実行中の読取に失敗し得ると説明されています。交換の計画には、キーの有効性と、保管場所を読める権限・可用性の両方が必要です。

## 保存先を替えても、起動済みのコピーは替わらない

次は、**自分のPCのNode.js**で動かせる架空例です。Node.jsを用意していない人は、コード下の結果だけでも読み進められます。`demo-A`と`demo-B`は版の名前で、キーの値ではありません。環境変数やファイル、ネットワークは読み書きしません。

```js
let savedVersion = "demo-A";
function startClient() {
  return { version: savedVersion };
}
const oldClient = startClient();
savedVersion = "demo-B";
const newClient = startClient();

// 発行元でBだけが有効になった状態を、架空の集合で表す。
const acceptedVersions = new Set(["demo-B"]);
function result(client) {
  return acceptedVersions.has(client.version) ? "受理" : "拒否";
}
console.log("保存先:", savedVersion);
console.log("起動済み:", oldClient.version, result(oldClient));
console.log("新しく起動:", newClient.version, result(newClient));
```

結果はこうなります。

```text
保存先: demo-B
起動済み: demo-A 拒否
新しく起動: demo-B 受理
```

保存先はBでも、先に作ったクライアントはAです。この例の拒否は、集合をBだけにした結果です。**実際のAPIキーを失効させるコードではありません。** 実サービスでは、発行元での失効と反映時間、アプリの読込方法を確かめます。

<RotationComparison />

「古い版が残るか」と「古い版が接続先に受理されるか」は別の問いです。両方を分けて確認すると、更新漏れによる停止と、古いキーが使えるまま残るリスクを区別できます。

## 通常の交換と、漏えいしたキーへの対応を分ける

漏えいの兆候がない計画的な交換なら、提供元が複数キーの併用を認めている場合に、新旧を短期間重ねて切り替える方法があります。キーが一つだけのサービスでは、この方法をそのまま使えません。メンテナンス時間や別の認証方法など、提供元の手順に合わせます。

<RotationVisual kind="planned" />

新しいキーでは、接続成功だけでなく、必要な権限・対象のアカウント・テスト環境か本番かも照合します。権限が足りないキーや、別のプロジェクトのキーを保存しても、文字列としての更新は成功してしまいます。

**漏えいした、または漏えいを疑う根拠がある場合は、無停止の切替を待ち続けません。** 発行元の事故対応手順に従い、悪用を止めるための迅速な失効や権限制限を判断します。停止の影響と不正利用の影響を比較し、接続先の管理者へ連絡します。詳しくは[漏えい時の対応](/ai-security-playbook/learn/incident-response/)へ。

<RotationVisual kind="incident" />

保管サービスの古い版を無効にする操作と、外部API側でキーを失効する操作は別です。保存先から消しただけで、既に持ち出されたキーまで使えなくなったとは判断できません。

<CatGuide pose="point" title="キーの値を見せずに、使う版を追う">
確認には、公開して差し支えない内部の版名とリリース・実行IDを対応付けます。キーそのもの、キーを含む環境変数一覧、接続ヘッダーをAIや公開ログへ貼らないでください。
</CatGuide>

## 保管場所の事故が、接続先のキー交換につながった

**分類：事故の公表。** CircleCIは2023年1月4日に利用者へ事故を通知し、1月12日の当事者報告で、シークレットのローテーションと失効を呼びかけました。[CircleCIの事故報告](https://circleci.com/blog/jan-4-2023-incident-report/)

ここからの学びは、保管・実行基盤側の事故でも、そこから利用する外部サービスの認証情報が対応対象になり得ることです。全利用者が不正利用されたという意味ではありません。自分の対象期間・保管していた情報・接続先は、当事者の通知と自分の記録で照合します。

別の運用例として、numekudiさんの[シークレット更新の記事](https://zenn.dev/numekudi/articles/a3a4ae380d125a)は、保存値だけでなく、実行中のアプリや定期処理への反映を取り上げています。これは著者による運用報告であり、上のCircleCI事故と同じ出来事ではありません。本教材の架空例も、原記事の環境を再現した実験ではありません。

## Webが動いていても、定期処理は別に確かめる

**ジョブ**は、集計や通知など、決まった処理を実行して終わる仕事です。Webアプリとは別の設定、別の起動時刻、別のキーを持つことがあります。

<RotationVisual kind="inventory" />

棚卸しでは、公開中のリリースだけでなく、まだリクエストが届く古い版、別URLで呼べる版、実行中のジョブ、次回の定期実行、再試行や手動実行の設定も見ます。利用先を特定できないキーは、「全部更新できた」としません。

確認のために、本番の請求・メール送信・更新ジョブを重ねて実行しないでください。提供元が用意する安全なテスト操作や、影響を限定した検証方法を選びます。ヘルスチェックの成功が、外部APIへ新しいキーで接続した証拠になるとは限りません。

キーごとの利用記録が発行元で見られるなら、旧キーの使用を追う助けになります。ただし、夜間だけ動く処理は昼間に記録がなくても不思議ではありません。**利用記録がないことだけで、すべての旧実行がなくなったとは断定しません。**

## 一人でも、3つの役割で見直す

### 利用先を把握する人：どこで使うかをそろえる

Web、本番とテスト、定期処理、CI、管理用の実行環境を一覧にします。各利用先の担当・設定名・読込時点・次の実行を記録し、分からない場所は未確認として残します。アプリ画面の成功だけで全体を代表させません。

### アプリを更新する人：読み込んだ版を実行と結び付ける

保存先の版と、反映したリリース・ジョブ定義・実行IDを照合します。起動済みのクライアントを更新する必要があるかは、実装で確認します。ログに必要なのは接続結果と安全な版の識別であり、キーの内容ではありません。

### 発行元を管理する人：旧キーの失効を確かめる

新旧併用の可否、キーの権限、失効操作と反映時間を確認します。失効後に新しい実行が動くことと、旧キーが無効なことを、提供元が認める手段で確認します。漏えいなら通常更新とは別の優先度で判断します。

個人開発では同じ人が担当して構いません。AIには一覧や設定差分の整理を頼めますが、実キーを渡す必要はありません。AIの「更新済み」は、実行記録と失効状態の代わりにはなりません。

## 交換が届いたと判断するための証拠

- **利用先：** Web・定期処理・CIなどの利用先と、今回対象か対象外かが分かる一覧がある。不明な利用先は完了扱いにしない。
- **新しい版：** 保存先の版と、必要な権限・アカウント・環境を照合した記録がある。キーの値は記録に含めない。
- **稼働への反映：** リリースや実行IDと読込版の対応、影響を限定した接続確認の結果がある。保存の成功だけで終えない。
- **旧実行：** 古い版への流量・別URL・実行中/次回のジョブを確認し、残る対象と対応期限が分かる。
- **失効後：** 発行元での旧キー失効状態と、新しい版での動作結果がある。失効状態を確認できなければ未確認とする。
- **異常時：** 誰へ連絡し、何を止め、どの安全な版へ戻すかが決まっている。漏えいキーを復活させる復旧案にしない。

## 次の定期実行まで、更新を追う

<RotationVisual kind="finish" />

通常更新でも、古いキーを失効した後の動作まで見て一区切りです。次回の定期実行が未確認なら、予定と確認担当を残します。エラー増加や外部APIの拒否を見たら、値を表示せず、利用先・版・実行時刻から切り分けます。

以前のアプリへ**ロールバック**、つまり戻す場合も注意が必要です。古いリリースが失効済みのキーを参照していれば、戻したことで接続できなくなります。復旧できるコードの版と、有効で適切なキーの組み合わせを考えます。

また、署名用や暗号化用の鍵は別の設計が必要です。交換が既存のログイン状態や暗号化済みデータへ影響する場合があり、APIキーの手順をそのまま流用しません。

<CatGuide pose="peek-side" title="替えたか、ではなく届いたか">
保存先の更新、新しい実行の成功、旧キーの失効。その3つをつなぐと、翌朝の処理まで見渡せます。
</CatGuide>
