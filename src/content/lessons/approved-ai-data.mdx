会社が契約したAIで、顧客からの問い合わせを整理しています。利用手順には「この業務では顧客情報の利用可」。契約上も、入力をモデルの学習には使わないと確認されています。

それでも毎回、すべての名前や住所を消さないといけないのでしょうか。

**一律にそうとは限りません。会社が承認した用途と取扱条件に合い、必要な確認が済んだ範囲で、業務に必要な個人情報を使える場合があります。** 学習への非利用は、その判断を支える条件の一つです。

この記事は、**会社や個人事業で、顧客の文章・表・文書をAIで扱う人**に向けたものです。仕事に必要な個人情報を、認められた範囲で使うための確認を整理します。

## 個人情報を使える業務はある。許可の単位をそろえる

「このAIを使ってよい」という案内には、範囲があります。まず、**利用目的**、つまり何の仕事のために情報を使うのかを確かめます。同じ問い合わせメールでも、文章の分類と、実際の配送先の照合では必要な情報が違います。

**ワークスペース**は、組織のメンバーや設定をまとめる作業場所です。会社の契約が適用される場所と、自分の個人アカウントを区別します。会社メールでログインできることだけで、目的の契約や設定が適用されているとは判断しません。

<EnterpriseVisual kind="scope" />

例えば、会社が「会社ワークスペースで、通常の配送問い合わせを整理し、担当部署内で共有する」と承認しているなら、必要な宛名や配送先を扱う運用を設計できます。一方、人事の健康情報、別の目的への転用、社外ツールへの転送まで認められたとは限りません。

これは架空の承認例です。実際には、**用途・情報の種類・サービスと機能・利用者・出力先**が、自社の手順に合っているかを見ます。毎回ゼロから許可を取り直すより、承認された業務と、その範囲を利用者が確認できる形にしておくと判断しやすくなります。

<CatGuide pose="point" title="「この仕事で使える」が分かる案内へ">
サービス名だけでなく、使える業務と情報、使う場所、共有する相手をそろえます。範囲内なら手順に沿って進み、変わる部分だけを確認します。
</CatGuide>

## 企業向けと、個人向け有料版を混同しない

製品名や料金だけで、同じ契約条件とは決まりません。**既定**は、特に変更していないときの扱い。**オプトアウト**は、対象の利用をしない設定を選ぶことです。

<EnterpriseVisual kind="plans" />

2026年10月24日に確認した公式説明では、次のように対象が分かれています。ここは、各社の全機能や個別契約を同一条件と評価する比較ではありません。

- **ChatGPT Business・EnterpriseなどとAPI：** OpenAIは業務データを既定で学習に使わないと説明しています。明示的に提供するフィードバック等は別に確認します。[OpenAI：企業データの取扱い](https://openai.com/enterprise-privacy/)
- **個人のChatGPT Free・Plus・Pro：** 「Improve the model for everyone」をオフにすると、新しい会話は学習に使われません。履歴を消す設定ではなく、フィードバック送信にも別の扱いがあります。**Plus・Proの料金を払うこと自体は、この設定と同じ意味ではありません。** [ChatGPTのデータコントロール](https://help.openai.com/en/articles/7730893-data-controls-in-chatgpt)
- **Claudeの商用製品：** AnthropicはClaude for WorkやAPIの入出力を既定で学習に使わないと説明し、フィードバック等の例外も示しています。個人のPro・Maxとは区別します。[Anthropic：商用製品の学習利用](https://privacy.claude.com/en/articles/7996868-is-my-data-used-for-model-training)
- **Microsoftの企業データ保護が適用されるCopilot：** プロンプト・応答・Microsoft Graph経由のデータを基盤モデルの学習に使わないと説明しています。適用条件と利用できる管理機能は契約・アカウント・機能を照合します。[Microsoft：企業データ保護](https://learn.microsoft.com/en-us/microsoft-365/copilot/enterprise-data-protection)

同じ画面のように見えても、個人と会社の作業場所を切り替えると条件が変わる場合があります。自分の画面に表示される所属先と、会社が指定した入口を見比べてください。アプリからAPIを使う場合も、そのアプリ自身のログや保存先は別に確認します。

**個人向け有料版でも、設定や契約等の条件を確認し、組織がその用途を認める場合はあります。** 企業向けという名前だけを唯一の許可条件にする必要はありません。反対に、個人で学習をオフにしたことだけでは、会社の顧客情報を移す許可までは得られません。

## 学習の外にも、保存・閲覧・送信の条件がある

モデルの学習は、データの扱いの一部です。回答を作る処理、会話やファイルの保存、管理や安全対策のためのアクセス、他のツールへの送信は別に考えます。

<EnterpriseVisual kind="handling" />

例えば、会話を保存して担当者が引き継ぐ運用なら、保存は業務に必要な機能です。保存があることを直ちに危険とするのではなく、**誰が使い、いつまで残し、何のために閲覧できるか**が合っているかを見ます。

会社の管理者が、プランや設定に応じた監査・記録の仕組みを使える場合もあります。「学習しない」から、会社の管理やサービス運用を含むすべての人に閲覧不能、と読み替えません。一方で、すべての管理者が全会話を自由に見られるとも決め付けず、実際の権限と機能を確認します。

**DPA**は、データの処理について定める契約です。学習への利用だけでなく、委託先、保持、削除、事故時の連絡などについて、自社に適用される契約や管理者の案内を確認する材料になります。契約名称があるだけで、あらゆるデータの利用を認める証明にはなりません。

## 連携やフィードバックを使うと、経路が増える

社内資料を読む**コネクタ**、外部の処理を呼ぶツール、Web検索、回答の共有などを使うと、入力した会話だけでは見えない経路が加わります。

<EnterpriseVisual kind="connections" />

例えば、社内での問い合わせ整理は承認されていても、その内容を未審査の外部アプリへ渡してよいとは限りません。連携する機能がどの情報を取得し、どこへ送るかを確認します。Microsoftの公式説明も、Web検索やエージェントを含む機能の条件を区別しています。[企業データ保護の対象と留意点](https://learn.microsoft.com/en-us/microsoft-365/copilot/enterprise-data-protection)

また、「役に立った」「問題がある」といったフィードバックの送信は、通常の会話とは扱いが変わる場合があります。業務データを使った会話で送信する前に、提供元の説明と会社の運用を見ます。利用者が毎回迷わないよう、管理機能で制御できる範囲も担当者が検討します。

<CatGuide pose="think" title="追加した機能の先まで見る">
AI本体で確認した条件が、接続先にもそのまま適用されるとは限りません。機能を増やすときは、情報の行き先が増えるかを確かめましょう。
</CatGuide>

## 必要な実データを、用途に合わせて残す

次は、承認された業務に応じて項目を選ぶ**架空の設計例**です。すべてのデータはダミーで、個人情報を取得したり、AIへ送信したりしません。自分のPCのNode.jsで動かせます。実行しない人も、結果から違いを追えます。

「問い合わせ分類」には内容と案件IDを使い、「配送先照合」には案件ID・宛名・住所を使う、という架空のルールにします。**法令や社内の許可を自動判定するコードではありません。** 実運用では、認められた目的と項目を確認してから、このような設計へ落とします。

```js
const fieldsByTask = {
  "問い合わせ分類": ["caseId", "body"],
  "配送先照合": ["caseId", "recipient", "address"],
};
function selectFields(task, record) {
  if (!Object.hasOwn(fieldsByTask, task)) throw new Error("用途が未登録");
  const fields = fieldsByTask[task];
  if (fields.some((key) => !Object.hasOwn(record, key))) {
    throw new Error("必要な項目が不足");
  }
  return Object.fromEntries(fields.map((key) => [key, record[key]]));
}
const demo = {
  caseId: "DEMO-014",
  body: "配送日の相談",
  recipient: "架空の受取人",
  address: "架空の配送先",
  internalNote: "この作業では不要な社内メモ",
};
console.log("分類:", JSON.stringify(selectFields("問い合わせ分類", demo)));
console.log("照合:", JSON.stringify(selectFields("配送先照合", demo)));
```

```text
分類: {"caseId":"DEMO-014","body":"配送日の相談"}
照合: {"caseId":"DEMO-014","recipient":"架空の受取人","address":"架空の配送先"}
```

同じ元データでも、使う項目が変わります。分類では宛名・住所を外し、照合では必要な項目として残しています。両方とも、今回不要な社内メモは送りません。

<EnterpriseVisual kind="fields" />

このコードは項目名だけを選びます。`body`に住所や病歴が書いてあれば、その文字まで自動で除去するわけではありません。IDがあれば個人へ結び付く場合もあり、匿名化されたという結果でもありません。実際には、選んだ項目の中身と、利用目的への適合も確認します。

実データを使えることと、AIの結果が正しいことも別です。例えば配送先の抽出結果は元の依頼と照合し、欠けた住所をAIが推測で補っていないかを見ます。読み取り・下書きまで認めた手順を、実際の発送や顧客情報の更新までの許可に広げません。

未登録の用途や必要項目の不足でエラーになったら、全項目を送る処理へ切り替えません。用途の追加や項目の変更が適切かを見直します。ここまでの例はデータ選択の練習であり、提供元の処理を再現するものではありません。

## 個人情報保護の注意喚起も、一律禁止とは違う

個人情報保護委員会は2023年6月2日の注意喚起で、事業者が入力する場合の利用目的との関係や、提供者による機械学習への利用等の確認を示しています。個人情報を含む入力を、すべて禁止するという書き方ではありません。[個人情報保護委員会の注意喚起](https://www.ppc.go.jp/files/pdf/230602_alert_generative_AI_service.pdf)

ただし、「学習に使わない」ことだけで、個別の法令・契約・会社のルールをすべて満たすとは判断できません。必要な手続はデータ、利用目的、契約関係などで異なります。すべての利用に本人同意が必須とも、同意が不要とも一律に決めず、担当者が条件を確認します。

個人事業主の場合も、顧客の情報を扱う側として確認します。会社の管理者がいないからといって、サービスの非学習設定だけを判断根拠にはしません。必要なら取引先の管理担当や、個人情報の取扱いを相談できる専門家へ、情報を広めずに相談します。

## 学習とは別の経路で、公表された脆弱性

**分類：脆弱性の公表。** Microsoftが2025年6月11日に公表したCVE-2025-32711は、当時のMicrosoft 365 CopilotにおけるAIへの命令の混入により、情報がネットワーク経由で開示され得る問題です。[Microsoftが登録したCVE記録](https://www.cve.org/CVERecord?id=CVE-2025-32711) / [提供元の対応情報](https://msrc.microsoft.com/update-guide/vulnerability/CVE-2025-32711)

この公表から考えるのは、モデルの学習とは別に、読む権限や外へ出す経路も確認する必要があるということです。個人情報を入力した全利用者が被害を受けたという意味ではありません。Microsoftは対策済みで利用者の対応は不要と説明し、公表時の悪用評価も「なし」としています。現在も同じ問題が未修正だと示すものではありません。

企業向けサービスを使うことを否定する事例ではありません。契約上の保護、サービス側の対策、接続先や権限の設計を組み合わせ、認められた範囲で使うための教訓です。

## 誰が、何を決めておくか

### 利用者：認められた仕事と、今の画面を合わせる

会社が指定した作業場所・用途・情報の範囲を確認します。範囲内で必要な情報なら手順に沿って使えます。新しい種類のデータ、個人の作業場所、追加した外部ツールなど、条件が変わる部分を相談します。回答を別の相手へ共有する場合は、その相手に見せてよい内容かも確かめます。

### 管理者：使える範囲を利用者へ伝える

契約する製品と設定を照合し、保持・閲覧・接続・共有・フィードバックの扱いを決めます。承認済み用途と禁止・要相談の例、問い合わせ先を短く示します。部署異動や退職時のアクセス、資料側の共有設定も見直します。

### データと契約の担当：目的と取扱条件を確認する

どの情報を何の目的で扱うか、必要な法令・契約上の条件、提供元や接続先の扱いを確認します。**企業向けだから全面可、個人向けだから常に不可、という製品名だけの線引きにせず、実際の条件を明確にします。**

アプリを作る人は、その決定を送信項目・権限・保存・監査の設計へ反映します。利用者の画面で入力を絞っても、裏側のコードが全件を送っていれば同じ運用になりません。

## 入力に進むための、具体的な確認

- **目的と情報：** 承認された業務と、扱える情報の種類・必要な項目が分かる。用途を変える場合は同じ許可として扱わない。
- **適用先：** 使う製品・プラン・アカウント・ワークスペースが、会社の案内や契約の対象と一致している。
- **学習と例外：** 非学習の既定または設定、その対象、フィードバック等の別経路を公式資料で照合した。
- **保存と閲覧：** 履歴・ファイル・ログの保持、閲覧権限、削除や監査の運用が分かる。保存があることと公開を混同しない。
- **接続と共有：** 追加ツールや検索、出力先を確認し、認められた範囲と一致している。
- **入力内容：** 必要な実データを残し、不要な項目や添付の別部分を除いた。選択後の自由記述も見た。
- **条件変更：** 新用途・機能・契約変更時の確認先が分かる。未確認を「学習オフだから可」で埋めない。

## 承認の範囲が変わるときに、見直す

<EnterpriseVisual kind="review" />

日常の承認済み業務を、毎回一から審査する必要があるとは限りません。新しい機能、データの種類、接続先、共有先が増えたときに、何が変わるかを確認できる運用にします。製品条件が変わった場合は、確認日と適用範囲を更新します。

<CatGuide pose="peek-side" title="使える条件をそろえて、仕事を進めよう">
実名を全部消すことだけが対策ではありません。仕事に必要な情報を、認められた場所と範囲で扱える状態を目指します。
</CatGuide>
