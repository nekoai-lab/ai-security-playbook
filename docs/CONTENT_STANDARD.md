# 教材の品質ルール / 2026-10-24

目的は記事数を増やすことではなく、AIを使う人・AIで作る人が対象を理解し、具体的な確認と判断へ進めること。非エンジニアを想定し、専門用語は初出で説明する。

## 公開する教材の必須要素

1. 対象と前提: 誰の、どの環境・操作を扱うか。対象外も必要な範囲で明記。
2. 仕組み: 図解または関係・処理の順序で、なぜリスクが生じるか説明。
3. 想定リスク: 守る対象、起きる条件、起きた場合の影響を具体化。「危険」「注意」だけで済ませない。
4. 過去の事例: 発生日/公表日、一次資料、確認された事実、未確認の範囲、学びを記載。実際の事故・公表された脆弱性・研究上の再現実験・架空例を区別。被害件数や悪用を推測しない。適切な実例を確認できなければ未確認と理由を示し、作らない。
5. 誰が何を確認するか: 利用者、個人開発者、管理者/提供元などの役割ごとに、対象、確認方法、判断できること/できないことを示す。一人で兼任する場合も操作対象を混同しない。
6. 具体的な確認と判断例: 自分が管理するテスト対象や架空データで確認できる手順。結果の意味と、止める/相談する条件も示す。
7. 確認チェックリスト: 「確認した」だけでなく、完了と判断する証拠を各項目へ。未確認・対象外を安全確認と数えない。入力フォームやダウンロードは不要。
8. 次の行動: 前提教材、関連手順、相談先の種類、運用で再確認する契機へつなげる。
9. 一次資料と確認日: 主張の近くに根拠を置き、出典一覧と情報確認日を残す。事実、教材の推奨、架空例を混同しない。

## やらないこと

- 概要・ニュース要約・一般的な注意だけで1教材とすること。
- AIの自己申告・画面の表示・チェック印だけで安全を保証すること。
- 脆弱性の存在を、その環境での悪用成立や侵害の証明として扱うこと。
- 非エンジニアへ説明なく本番変更、権限解除、秘密の貼付、PoC、強制停止・削除を勧めること。
- 原稿名、私的作業履歴、制作の都合など作成者向け文章を公開本文へ残すこと。

## レビューと検査

構成・参照の機械検査と、内容の妥当性のレビューを分ける。文字数で厚みを保証しない。出典と事故分類、権限/対象範囲、チェックリストの証拠、初学者が次に取る行動、時点と未確認範囲を読み直す。
既存の5教材は導入前の教材として監査結果へ分けて記載し、全教材が本ルールを満たしたと誤表示しない。新規教材は必須構成がない場合に検査を失敗させ、後から追加する教材を例外へ入れない。デザインのしきい値は変更しない。

## 読者を起点にした構成（qualityVersion: 2）

対象読者が「自分のことかもしれない」と分かる場面から始める。目次は記事固有の疑問にし、導入→具体例→図で仕組み→コード/画面と結果→自分の確認→次の判断へつなげる。全記事に同じ9見出しを強制しない。本文の長さや図の数だけでは合格としない。

既存v1の必須構成は維持する。自然な見出しを使うv2ではreviewSectionsでaudience/mechanism/risks/case/roles/exercise/checklist/next/sourcesの9項目を実在のH2へ対応させる。audienceだけは「導入」も指定可能。必須項目を減らす変更ではない。対応先の欠落、分類・年代・出典、3か所以上の役割別確認、証拠付きチェック、仕組みの図、コードと観察可能な結果を検査する。結果の意味・適用範囲・内容の妥当性は別途レビューする。

図は説明上の仕事を持たせる。導入の場面、種類の比較、情報の移動、権限の境界、確認箇所などを示す。本文の文字を箱へ写すだけにしない。既存の猫Cは案内、ロゴAは発行主体として再利用する。図の文字は実テキストを優先し、スマホと文字200%で読めるようにする。コードはダミーと実行場所を明記し、教材と同じ条件で確かめる。実行しない読者も結果を追える説明を付ける。

公開記事へ作者用の作業記録を混ぜない。coverageマップや検証結果はソース/設計記録へ。新教材を既存対象の一覧へ足して検査を回避しない。v2はコードと結果を含む今回の実践教材を対象とする。コードが目的に合わない教材は、無意味なコードを足さず、v1の基準を保ちながら別途適切な検査契約を設計する。

## 場面の挿絵と仕組みの図の使い分け

読者が場面を思い浮かべやすい探検猫の挿絵を、導入や話題の転換へ積極的に使う（ユーザー承認）。同じ画像を全段落へ反復せず、設定に迷う・動作を調べるなど記事固有の場面に合わせる。挿絵はイメージとして扱い、事実や安全性の証明にしない。情報の流れ・権限・確認手順は実テキストの図で示す。挿絵の中にコードや確認すべき文字を焼き込まない。画像の読込サイズ・遅延読込・寸法予約・代替説明も確認する。

## 既に確認している読者の、次の疑問を扱う

「気をつける」「確認する」で止めず、読者が行った確認で分かる範囲と、まだ分からない境界を具体化する。AIの警告や一般的な対策を知らない人という前提で、わざと低い問いを作らない。用語を説明し、場面・仕組み・例と結果・確認の根拠までつなぐ。網羅性は文字数で判断せず、対象の前提、情報経路、権限、失敗時、担当、次の判断をレビューする。

教材の少ないテーマも、空の一覧や同じ絞り込みリンクで済ませない。固有の状況、最初の解説、具体的な疑問と該当節への導線、隣接するテーマを整える。記事を分割して件数だけ増やさない。

## 冒頭で「読む価値」を判断できる案内 / 2026-10-24

最初の画面と導入で、次を短く示す。架空の不注意を決めつけたり、不安だけで引きつけたりしない。

- **こんな時に**：読者が今行っている作業・困っている場面。
- **読んで分かること**：読後にできる判断・確認。安全を保証する表現にしない。
- **対象と前提**：誰のどの環境を扱うか、必要な準備や前提知識。
- **最初の全体像**：早い段階の図解で、扱う範囲と情報・処理の流れを示す。

必ず同じ四つの箱を増やすのではなく、既存の要約や導入と重複させずに案内する。初学者向けでも、すでに確認した人の次の疑問を尊重する。

## 情報の厚みを保ち、理解しやすい形式を選ぶ / 2026-10-24

長い文章を連続させない。説明の目的に合わせて形式を選び、本文との重複を削る。

| 伝える内容 | 優先する形式 |
| --- | --- |
| 仕組み・関係・処理の順序 | 実テキストの解説図 |
| 要点・注意点・確認項目 | 短い箇条書き |
| 条件や選択肢の違い | 比較表 |
| 実際の動き | 小さな具体例・安全なコードと観察できる結果 |
| 理由・背景・条件のつながり | 一段落一論点の短い文章 |

図や箇条書きにするために、成立条件・例外・出典・不確実性を落とさない。猫の挿絵は場面や注目点を助ける位置に置き、仕組みを説明する図の代わりにしない。図表もスマホ・文字200%・読み上げ順で確認する。レビューでは「誰に、どんな時に、何の判断を支えるか」が冒頭で分かるか、長文の塊・重複・装飾だけの図がないかを確認する。

この追加ルールは今後の新規・改訂に適用する。既存記事すべての改訂完了を意味しない。
