# 教材の品質ルール v1 / 2026-10-24

目的は記事数を増やすことではなく、AIを使う人・AIで作る人が対象を理解し、具体的な確認と判断へ進めること。非エンジニアを想定し、専門用語は初出で説明する。

## 公開する教材の必須要素

1. 対象と前提: 誰の、どの環境・操作を扱うか。対象外も必要な範囲で明記。
2. 仕組み: 図解または関係・処理の順序で、なぜリスクが生じるか説明。
3. 想定リスク: 守る対象、起きる条件、起きた場合の影響を具体化。「危険」「注意」だけで済ませない。
4. 過去の事例: 発生日/公表日、一次資料、確認された事実、未確認の範囲、学びを記載。実際の事故・公表された脆弱性・研究上の再現実験・架空例を区別。被害件数や悪用を推測しない。適切な実例を確認できなければ未確認と理由を示し、作らない。
5. 誰が何を確認するか: 利用者、個人開発者、管理者/提供元などの役割ごとに、対象、確認方法、判断できること/できないことを示す。一人で兼任する場合も操作対象を混同しない。
6. 具体的な確認と判断例: 自分が管理するテスト対象や架空データで確認できる手順。結果の意味と、止める/相談する条件も示す。
7. 確認チェックリスト: 「確認した」だけでなく、完了と判断する証拠を各項目へ。未確認・対象外を安全確認と数えない。入力フォームやダウンロードは不要。
8. 次の行動: 前提教材、関連手順、相談先の種類、運用で再確認する契機へつなげる。
9. 一次資料と確認日: 主張の近くに根拠を置き、出典一覧と情報確認日を残す。事実、教材の推奨、架空例を混同しない。

## やらないこと

- 概要・ニュース要約・一般的な注意だけで1教材とすること。
- AIの自己申告・画面の表示・チェック印だけで安全を保証すること。
- 脆弱性の存在を、その環境での悪用成立や侵害の証明として扱うこと。
- 非エンジニアへ説明なく本番変更、権限解除、秘密の貼付、PoC、強制停止・削除を勧めること。
- 原稿名、私的作業履歴、制作の都合など作成者向け文章を公開本文へ残すこと。

## レビューと検査

構成・参照の機械検査と、内容の妥当性のレビューを分ける。文字数で厚みを保証しない。出典と事故分類、権限/対象範囲、チェックリストの証拠、初学者が次に取る行動、時点と未確認範囲を読み直す。
既存の5教材は導入前の教材として監査結果へ分けて記載し、全教材が本ルールを満たしたと誤表示しない。新規教材は必須構成がない場合に検査を失敗させ、後から追加する教材を例外へ入れない。デザインのしきい値は変更しない。
