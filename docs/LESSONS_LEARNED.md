# 作業の教訓と次回の判断基準

## 2026-10-26 セキュリティ更新記事と自動公開の分離

### 起きたこと

更新記事・画面・日報取り込み・自動公開判定をPR #51にまとめた。自動公開基盤の独立レビューで修正が続き、記事と画面が完成していても公開できなかった。古いレビュー結果や古い日報の扱いなど、実際に修正が必要な問題も見つかった。レビュー自体を不要だったとは扱わない。

記事側をPR #52へ分離したところ、その変更範囲の独立レビューは1回で合格し、検証と本番URLの確認を経て公開できた。自動公開基盤は下書きPRとして保全し、定期実行も明示的な有効化までは公開処理をしない設定にした。1件の結果だけで、今後の所要時間や安全性の改善を保証しない。

### 原因

- 独立して提供できる成果物を、一つの完了条件に結びつけた。
- 自動公開で何を信頼し、古い入力・競合・訂正をどう扱うかの設計確認が遅かった。
- 修正後の再確認範囲と、レビュー対象のコミットを管理しきれなかった。
- 「記事完成」「PR作成」「レビュー合格」「本番公開」を進捗説明で十分に区別できず、未解決事項が残るのに「レビューと公開だけ」と説明した。

### 次回の開始時に決めること

1. 読者に届ける最小の成果と、その公開条件を先に書く。
2. 記事公開、日報からの下書き生成、自動公開の有効化を別PRにする。先の段階が後の段階の完成を待つ構造にしない。
3. 公開・権限・削除を伴う仕組みは、入力の信頼境界、古い版、競合、再実行、失敗時の停止と復旧を実装前に整理する。
4. 必須テスト、画面確認、独立レビューの範囲と完了条件を決める。必要な検証を省略するための分割にはしない。

### レビューと検証

- 初回レビューは対象PRの全体を確認し、確認できた問題をまとめて返す。
- 修正確認は指摘の解消とその影響を中心に行う。新たな重大問題が見つかれば止める。
- 2回で収束しない場合は、レビューを打ち切って合格にせず、未解決部分の分割や設計の見直しを判断する。
- レビュー対象SHAを固定し、結果のSHAと現在のHEADを照合する。古い合格を最新版の合格と扱わない。
- 検証範囲は変更とリポジトリの必須規則に従う。全画面検査の閾値緩和、対象除外、過去結果の流用で合格にしない。
- 待機中は同じレビューの重複起動や、関係ない追加改修を行わない。

### 公開と報告

- レビュー合格・CI成功と同一のコミットだけをマージする。
- 対象マージSHAのデプロイ成功と実URLの本文・HTTP状態を確認して初めて「公開済み」と伝える。
- 進捗は完成した部分、残る問題、現在の待機先を具体的に伝える。本人の確認待ちでなければそう明示する。
- 記事公開済みでも自動化未完成なら、両者を分けて報告する。
